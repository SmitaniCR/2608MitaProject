# モード5・6・7(明示的に依頼されたときだけ動くモード)

`SKILL.md`のモード0〜4が学習の通常の流れであるのに対し、ここにある3つは**学習者が
明示的に依頼したときだけ単発で動く**。頻度が低いため`SKILL.md`本体から分離してある。
該当するトリガーを受け取ったらこのファイルを読んでから実行する。

## モード5: チーム進捗の共有(要約メッセージの作成)

トリガー例: 「進捗をチームに共有して」「Teamsに貼る用の進捗をまとめて」

学習者ごとにリポジトリが別々のことが多いため、**ファイルを介した自動集約はしない**。
チームが実際に使っている手段にそのまま貼れる**短い要約テキストを作るだけ**にする。

- PROGRESS.mdから、現在Step(「進行中」の行、無ければ最も進んだ「完了」行)と
  Step0チェックリストの対応スコア(n/全項目数)を要約する。

  ```
  【SpringBoot学習】2026-08-16時点
  現在: Step6 バリデーションエラー(進行中)
  Step0基礎チェック: 10/全項目数 対応済み(例: 全16項目なら10/16)
  ```

- **書き出すのは要約のみ**: 個人のメモ、実証箇所の詳細、つまずいた内容は含めない。
- **送信・投稿は行わない**: 要約テキストの提示だけで、実際に伝えるのはユーザー自身。
  副作用のある操作は一切発生しない。

## モード6: 修了確認(全体棚卸し)

トリガー例: 「全部終わったか確認して」「修了できるか確認して」

CURRICULUM.mdの「修了基準」を満たしているかを、**リポジトリ全体を横断した最終棚卸し**として
確認するモード。

- まずPROGRESS.mdを見て、未完了の**必須**Step・Step0チェックリストの`未実証`項目があれば
  先に伝える(この時点で修了とは判定しない)。
  - **Step21以降(認可・ロギング・フロントエンド・React編、Step21〜36)はすべて任意/発展
    Stepであり、未完了・未着手でも修了判定から除外する**。これらを「未完了のため修了では
    ない」と報告してはいけない。必須Stepが揃っているなら、「任意メニューとして〇〇が
    残っています」のように修了可否とは区別して伝える。
    (Step20のSpring Securityは必須のため、この除外対象には含まれない——必須修了者は
    Step17の平文パスワードがStep20でハッシュ化に置き換わっていることを確認する。)
- 記録上すべて完了でも、**その記録を鵜呑みにしない**。主要なStepについて実際にリポジトリの
  コードを横断的に読み直し、完了条件が今も満たされているかを再確認する(退行・記録の
  付け忘れがあり得るため)。
- **記録とコードの不一致が確定した場合の直し方**:
  1. 合意を得た上で、**該当Stepの状態を「完了」から「進行中」に戻し、完了日を空にする**。
     「完了のままメモに注記だけ」はしない(状態が「完了」の限り以後のモード0・5・6が
     対応済みと数えるため)。
  2. `## 宿題`セクションに、何が満たされなくなったか・いつ完了と記録していたかを残す
     (例: `- [rest-api] ReportControllerがServiceを経由せずRepositoryを直接呼んでいる(2026-08-14に完了と記録したが退行)`)。
  3. Step0チェックリスト項目の退行も同じ考え方で`未実証`に戻し、`## 宿題`セクションに残す。
  4. コードを読んでも判断が付かない場合は状態を動かさず「保留」とする。**確定していない
     段階で状態列を戻さない**。
- 本当に修了基準を満たしていれば、学習内容・成長が見られた点・今後の発展メニューや実務への
  橋渡しを含めた**修了報告の要約**を作成する(モード5と同様、提示するだけ)。
- 一部だけ満たしていない場合は、部分的な達成状況も具体的に伝える。
- **そもそもコードを読めない場合は、修了とも未修了とも判定せず「保留」とする**。記録だけを
  根拠に修了と言わない。次に何が分かれば判定できるかを1点に絞って伝える。
  - 進捗ファイルとソースコードが別ディレクトリの場合、**学習者が明示的にパスを示したときに
    限りそのパスを読む**。読めなければ推測で探し回らない。恒久策として進捗ファイルを
    コード側リポジトリに移すことを提案してよい。
  - 貼られたコード片での確認に切り替えてよいが、**横断的な確認の代替にはならない**ことを
    合意した上で行い、修了報告にもその旨を残す。
- Step0チェックリストの実証箇所が空欄・定型文の項目は、記録を根拠にせずコードで裏を取り直す。

## モード7: 質問・回答の蓄積(FAQ化)

トリガー例: 「この質問と回答をFAQに残して」「今のやり取りを保存しておいて」

やり取りを将来の学習者にも役立つ知識として`references/faq.md`に蓄積するモード。

- 対象の質問・回答を、**個人が特定される情報や会社固有の機密情報を含まない形に一般化**する。
  一般化すると意味を失う、あるいは機密を取り除ききれない場合は保存を見送り、その旨を伝える。
  学習者が別の一般化案(伏せ字化等)を提案してきたら、その案で再検討する。**再検討の結果、
  それでも意味を失う・機密が残ると判断したのは1回までとし、2回目の再検討では見送りか
  保存かをその場で決める**(別の理由を持ち出して見送りを繰り返さない)。
- どのStep(または「環境・ツール関連」)に関連するかを判断し、そのStepの`id`に対応する
  `references/faq.md`の見出しの下に追記してよいか、一般化した内容を見せた上で確認する。
  見出しが無ければ`## <Step名> <!-- id: xxx -->`の形式で新設してよいか確認する
  (番号は変更されうるため、見出しはidで管理する)。
- 既に似た内容があれば重複追加せず、既存項目の更新・統合を提案する。
- `references/faq.md`はスキル本体配下にあるため、コミット・共有の可否はユーザーの判断に
  委ねる(このモード自体がgit操作を行うことはない)。
